# 商策｜每日经营巡检技能卡产品汇报

**汇报角色：** AI 产品经理

**评审对象：** 产品、数据、工程与运营团队

**文档日期：** 2026-10-27
**当前阶段：** 技能卡与交互报告原型已形成；尚未接入 Hermes 网关、生产数据和外部通知

## 1. 产品概述与评审要点

我们要交付的主体是一个可复用的**「每日经营巡检」技能卡**。它把店长一次性提出的「大促后流量下降是否异常」扩展成每天都能按相同标准执行的经营检查：在授权范围内读取数据，判断哪些变化值得优先处理，给出可追溯的依据，并在下一次检查时带回上次问题的处理状态。**交互式 HTML 日报是技能的一项输出，不是技能本身。**

内部技能定义已写入 [`daily-business-pulse/SKILL.md`](../../.hermes/skills/daily-business-pulse/SKILL.md)；商家看到的是「每日巡检」的开启、设置、日报与待办，不需要理解底层术语。当前网页已经演示技能的一次执行和后续复盘，但没有在浏览器关闭后自动运行。

本次希望先评审两件事：**技能卡的业务契约是否足够窄且可信；能否以现有固定样例进入下一步 Hermes 网关接入验证。** 真实店铺接入是更后面的决策。

## 2. 业务问题与产品定位

目标用户是经营单店、缺少专职分析人员的中小商家店长。每天开店后，他需要从流量、用户、交易和搜索表现中判断「今天先处理什么」。现有经营诊断需要店长先发现异常、组织问题并主动提问；得到一次结论后，第二天是否继续核查也依赖店长自己记得回来。

每日经营巡检的定位是**可订阅的经营日报与待办**：每天按同一套规则检查已完成自然日的数据，告诉店长发生了什么、依据是什么、先做什么，以及上次问题后来怎样。经营诊断仍用于店长主动追问某个问题；巡检负责日常检查。诊断中值得持续关注的问题可以成为专项关注，但不会自动扩展成全店四维巡检。

这不是把旧问题保存成一个定时提醒。我们将单次诊断拆成「每次都相同的判断方法」和「每天都会变化的经营上下文」，再把前者固化为技能。

| 从单次诊断提取的内容 | 在技能卡里的处理 |
| --- | --- |
| 先确认店铺、日期、指标口径，再分析异常 | 固化为每次执行的前置校验；不在提示词里猜测权限与时间窗 |
| 看流量总量，再下钻到互斥来源渠道 | 固化为流量检查步骤；只有渠道与总量对账后才计算结构贡献 |
| 结论必须给出来源、分母与不确定性 | 固化为证据卡和停止条件；缺数时生成部分报告 |
| 店长处理后仍需观察下一天的数据 | 固化为持续事项、处理反馈和次日复核 |
| 原诊断能保存为专项关注 | 只继承原问题、流量指标、基线与证据，不自动扩大成全店四维订阅 |

随后把监控范围限定为**单店、只读、流量／用户／交易／搜索排名四维**。选择这四维，是为了覆盖店长开店后的基本判断，又避免把广告预算、改价或客户触达纳入同一个技能。这样技能既能跨日复用，也能用固定数据集检查输出是否一致。

## 3. 技能卡定义与使用边界

技能卡有两层：**商家可理解的订阅设置**，以及内部执行用的 [`SKILL.md`](../../.hermes/skills/daily-business-pulse/SKILL.md)。Markdown 文件带 `name`、`description`、`version` 等元信息，正文规定执行顺序、证据、失败停止、记忆和治理；页面上的设置只暴露店长有必要选择的项目。

| 卡片要素 | 当前定义 | 产品决策 |
| --- | --- | --- |
| 身份与版本 | `daily-business-pulse@1.0.0`，中文名称「每日经营巡检」 | 同一套判断方法可按版本评测、复用与回滚；内部版本不让商家手改 |
| 适用对象与权限 | 获授权的单店店长；默认只读 | 一次执行只处理一家店；不能从用户输入推断其他店铺权限 |
| 触发与日期 | 默认每日 09:00、北京时间；分析前一个已完成自然日 | 频率和时间属于订阅配置；真正到点触发由独立网关负责，`SKILL.md` 不会自行定时 |
| 监控范围 | 默认流量、用户、交易、搜索排名；可选非空子集 | 只取被选维度；诊断专项关注与全店巡检分别管理 |
| 提醒策略 | 仅重要异常、每次完成、或不提醒 | 报告生成与提醒送达分开记录，避免重跑时重复提醒 |
| 允许工具 | 四个分域只读查询、指标证据查询、处理反馈记录 | 不使用参数无限扩展的万能分析工具；反馈只写本产品状态，不改经营系统 |
| 执行步骤 | 授权与数据就绪 → 分域取数 → 确定性判断 → 证据核对 → 日报与待办 → 保存快照 | 步骤可观察、可中断，数据不足时不能伪装完整成功 |
| 输出 | 数据范围、今日重点、四维概况、优先事项、证据卡、待办、次日跟进和独立 HTML | 报告内容由数据与规则计算，HTML 只负责让结果可读、可操作 |
| 记忆 | 配置、历史报告、持续问题、处理反馈、否决建议与版本 | 每条反馈有业务生效日；旧日报补记不能覆盖较新状态 |
| 失败与停止 | 无权、无可信工具、日期无数据、口径冲突、超时、部分缺数 | 停止受影响结论并说明原因；有可靠数据的维度仍可交付部分日报 |
| 治理 | 反馈 → 改进候选 → 历史对照 → 人工审核 → 新版本／回滚 | 仅允许话术、FAQ、事项排序进入候选；口径、阈值、权限和资金动作不自动变更 |

商家端只需看到「开启每日巡检」「关注哪些变化」「什么时候检查」「何时提醒」等业务表达。技能身份、执行约束与规则维护留在内部，避免把工作台做成技术配置页。

### 技能文件与执行模块的分工

`SKILL.md` 定义**怎样做与何时停**，但它不会提供数据、自动触发任务或画出报告。现有 `.mjs` 文件是对这份契约的原型实现：分域取数、规则计算、状态保存、网页交互和 HTML 导出分别由不同模块承担。将来 Hermes 网关加载技能时，还需要把已授权数据工具和持久化接口接给它。反过来，只保留 `.mjs` 而没有独立技能定义，也无法清楚说明哪些判断可以跨店铺、跨日期复用，以及版本如何治理。

## 4. 技能执行流程与证据规则

1. **确认上下文。** 输入必须包含授权店铺、报告日期、所选维度、技能与指标版本；报告日期按北京时间自然日校验。无权或不支持的日期直接停止。
2. **只取需要的数据。** `queryTraffic`、`queryCustomers`、`queryTransactions`、`queryRanking` 分域读取；`getEvidence` 提供指标定义与来源。当前这些是项目内函数，尚不是 Hermes 可直接调用的远程工具。
3. **执行可复核规则。** 店铺 UV 相对参考预期下降至少 10% 且绝对缺口至少 200 人，才列为关注；付费渠道下降至少 15% 且缺口至少 200 人，才优先排查；同条件排名下降至少 5 位只作为线索。用户和交易没有可比基线时只展示观察值。
4. **检查数据质量。** 渠道明细必须与店铺 UV 对账；交易转化率必须有同口径访客分母；排名必须是同词、同设备、同地域、同采样条件。冲突或缺失时暂停对应判断，不补零、不借用别日值。
5. **组织证据和动作。** 每个异常附指标 ID、口径版本、定义、分子分母、时间窗、来源、血缘、取数时间及仍需核验的因素。建议先让店长核查计划、曝光或商品状态，不直接改预算。
6. **保存并等待反馈。** 报告按店铺、日期、技能版本和配置身份保存快照；送达另行去重。处理反馈记录状态、备注、生效日和修订序号，下次巡检用同一 `incidentId` 关联持续问题。

这条链路的关键边界是：**付费渠道缺口只是店铺总缺口的一部分，不是第二笔损失，也不是已证明的流量下降成因；「已处理」不等于「已恢复」。**

## 5. 状态记忆与规则治理

订阅能力不能只记住「每天 09:00」。它还要记住店长关心的维度、上一日的报告版本、哪些问题仍在持续、哪些建议被标为不适用、哪一天实际记录了处理。当前 [`radar-memory.mjs`](../../src/radar-memory.mjs) 在浏览器本地保存这些状态，区分报告生成与通知送达，并按业务日期选择反馈。生产形态需要服务端存储、租户隔离、授权删除和过期策略。

商家反馈不是直接改规则的许可。内部维护入口只允许把**表达、FAQ 或排序**作为改进候选，先对三日历史报告做前后对照，再由负责人批准发布新版本；发现问题可回滚。三日回放目前只是原型验证，不能替代真实环境的独立评测集、影子运行和灰度。指标口径、归因权重、权限和资金动作始终不进入自动学习范围。

## 6. Hermes 能力与本项目的对应关系

Hermes 提供技能、定时触发、记忆和版本治理等基础能力；这份巡检技能需要由我们定义店铺权限、指标口径、判断规则、报告内容和质量标准。两者的分工如下：

| 对应知识点 | 在每日巡检中的作用 | 当前进展与下一步 |
| --- | --- | --- |
| 技能层 | 用 [`SKILL.md`](../../.hermes/skills/daily-business-pulse/SKILL.md) 固定输入、取数顺序、证据要求、停止条件和输出结构，让同一方法可以按版本复用。 | 技能文件已写好；下一步验证 Hermes 能否识别并按契约调用。 |
| 网关与定时任务 | 在约定时间为获授权店铺发起巡检，记录运行状态，并处理暂停、重试与失败。 | 当前只有浏览器内的配置和执行演示；尚未连接网关，关掉页面后不会自动运行。 |
| 记忆层 | 保留订阅设置、历史日报、持续问题和店长反馈，让下一次巡检知道上次发生了什么。 | 原型保存在浏览器本地；接入时需迁至有权限控制的服务端存储。 |
| 自进化治理 | 从反馈中提出报告表达或事项排序的改进候选，经过历史对照、人工审核、发布和回滚。 | 已有原型流程；真实影子运行、独立评测和灰度尚未完成，经营指标与权限不自动修改。 |
| 从问答走向订阅 | 把店长主动发起的一次诊断，变成按日检查、交付报告、记录处理、次日复核的持续服务。 | 商家端链路可演示；真正的后台订阅依赖上述网关、数据与记忆接入。 |

## 7. 交互式经营日报

HTML 报告是技能执行后的**交付界面**：店长能从一句话重点进入异常、查看指标口径和来源、记录处理，并切换到下一日报告复核。当前样例的 11 月 14 日店铺 UV 为 6,000，参考预期 7,000；付费渠道缺口 500，占店铺额外缺口 1,000 的 50%。11 月 15 日付费缺口缩至 150，但报告不会把这一变化直接归因为店长的处理动作。

可独立打开的[交互式经营日报](经营巡检日报.html)支持三日切换、证据展开和本地反馈。样例日期在本文档日期之后，数值用于检验技能判断与交互，不是已发生的商家经营结果。独立文件中的反馈目前也不会同步回工作台。

## 9. 当前验证结果与实施边界

当前已核对 `SKILL.md` 的元信息与正文结构；固定情景下 71 项自动测试通过。已有走查覆盖手机与 PC 视口、日报至证据、诊断返回、处理反馈、次日跟进、导出和失败态；[页面截图](screenshots-v2/)记录了关键状态。这些验证证明技能契约对应的**原型行为**，不证明 Hermes 已加载技能，也不证明真实商家效果。

目前「开启巡检」只保存浏览器内配置并触发一次页面内更新；页面关闭后不会在约定时间自动运行。真实经营数据、服务端权限、后台定时、通知、跨设备记忆和在线影子治理均未接入。因此，技能卡可以评审，HTML 可以演示，但还不能把它称为已上线的订阅服务。

## 10. Hermes 网关接入计划

这四步是**接下来的安排**，本次不执行，也不要求先接入真实店铺数据。

1. **让 Hermes 识别技能。** 安装并配置 Hermes，在项目目录信任 [`SKILL.md`](../../.hermes/skills/daily-business-pulse/SKILL.md)，确认 `daily-business-pulse` 能被列出和手动调用；先用固定样例验证输入、输出与停止条件。
2. **接入持续运行的任务网关。** 启动 Gateway，创建挂载该技能的定时任务并指定项目工作目录；核对北京时间 09:00 对应的实际下次运行时刻，手动触发一次，检查暂停、重跑、失败和运行记录。任务不能只依赖店长的浏览器计时器。
3. **补齐浏览器外的数据与记忆接口。** 把现有四个本地查询能力封装成网关可调用的授权适配器；先接固定样例，再评估真实平台数据。将订阅、报告、反馈与送达状态迁出 `localStorage`，保留按店铺／日期／版本去重和数据质量降级。
4. **把结果送回工作台。** 将日报快照和送达状态写入网页可读取的受控存储，令商家页面展示最新报告、历史、暂停状态与失败原因；最后再接真实通知。完成数据授权、接收者校验和可靠性验证后，才讨论真实商家试点。

**评审所需决定：** 先确认技能卡的四维范围、证据与停止规则是否可接受；然后确定网关验证使用的运行环境和适配器负责人。现阶段保留功能分支，不把本地配置展示为真实后台订阅已生效。
