# 作业三｜「每日经营巡检」Skill 产品方案（PRD + 技能契约）

> **产品**：商策 · 商家经营分析 Agent  
> **能力**：每日经营雷达 / Daily Business Pulse  
> **文档版本**：v1.0，2026-10-24  
> **项目仓库**：[AuroraSunDev/fitness-audience-agent](https://github.com/AuroraSunDev/fitness-audience-agent)  
> **数据与能力声明**：这是教学演示设计；所有商家、指标、事件、报告、调度、通知、审批均为 Mock。2026 年 11 月日期是课程假设情景，不是已经发生的经营事实。  
> **要求来源**：第四节课作业三——设计「每日经营巡检」技能，从一次性问答升级成可订阅、可复用、可治理的能力；覆盖 Hermes 的技能层、调度网关、记忆层、自进化治理；监控流量、用户、交易、排名，并给出优化建议与可交互 HTML 报告。

## 0. 最终决策与范围

**只做一个平台、一项可订阅 Skill、一个店铺、一套前后一致的模拟经营数据。** 在已经完成作业二的原型基础上演进，而不是另起一个商家系统或新业务场景。作业二的「大促后流量下降诊断」负责深入分析；作业三的「每日巡检」负责按约定频率自动检查、主动发现异常、优先级排序、追踪动作与改善情况。

- **用户**：经营 1 家健身用品店铺、没有专职数据分析师的中小商家店长/运营负责人。
- **主端**：390px 左右手机端（商智 App 风格）；PC 自适应。
- **核心价值主张**：每天汇总重要变化，回答「今天先处理哪件事、为什么、怎么处理、处理后是否改善」，降低跨表查询和重复复盘的成本。
- **产品边界**：巡检只读；可以生成建议、模拟订阅和处理反馈；没有真实运行的云定时任务，不真实发送通知、不真实调广告预算、不宣称模型已经自主学习。
- **可验证但尚未验证的业务假设**：店长比起纯数值日报，更愿意使用有异常优先级、证据及行动闭环的巡检报告。尚无真实商家访谈和效果试验，不能把假设写成用户事实。

### 与作业一、二的关系

| 已有材料/能力 | 本作业如何使用 | 不能做出的宣称 |
|---|---|---|
| 作业一跨品类人群机会立项 | 沿用数据可信、只读优先、受控执行、KPI/风险治理的方法 | 不擅自把新增四维巡检写进原 MVP 已批准范围 |
| 作业二 S1–S7 大促后流量诊断 | 复用店铺身份、UV 口径、Mock 渠道、证据、诊断链路和错误恢复 | 不重复造第二套诊断引擎或第二个经营分析平台 |
| 作业二 S8 「大促后流量异常巡检」 | 作为新「每日经营巡检」的默认预设/配置入口和数据迁移来源 | 不能只把 S8 改标题就声称已有真正定时巡检 |

## 1. 真实工作流程与痛点假设

**典型早间工作任务（拟通过访谈验证）**：店长查昨日访客/来源渠道 → 查新老客/转化 → 查订单与 GMV → 查看重点 SKU 的搜索排名 → 查异常原因 → 做今日运营安排 → 隔天重复上述流程。

设计切口不是把四个图拼成日报，而是补齐三个工作断点：

1. **优先级断点**：同时十几个数字在变化，哪些需要立即处理？
2. **解释断点**：GMV 和流量下降是正常活动回落、渠道变化，还是统计口径问题？
3. **行动断点**：提出建议后，商家是否处理、后续有没有改善，系统是否记得？

待验证方法：约 5–10 次目标商家访谈；复盘最近 3 次异常处置流程；量化人工日报耗时、重复查询次数、能否复盘前次处理记录。教学项目无法访谈时，请把上述内容标成「待验证」而不是「访谈结论」。

## 2. 用户任务与关键产品流程

**用户故事 A｜首次订阅**：作为店长，我想选择需要监控的指标与提醒策略，以便每日收到与店铺实际有关的异常摘要。

**用户故事 B｜每日查看**：作为店长，我希望从一份报告了解昨日最值得处理的异常，点开后看到依据、影响范围和建议动作。

**用户故事 C｜处理闭环**：作为店长，我希望把异常标记为「待处理/已处理/不适用/暂缓」，第二天还能看到处理后的变化，而不是重复收到一样的话术。

**用户故事 D｜受控治理**：作为运营/产品负责人，我希望能看到技能的版本、执行日志、失败原因和待审改进提案，必要时停用或回滚。

### 信息结构

```text
商策（现有统一平台）
├── 经营诊断（保留作业二 S1–S8）
│   └── S8：保存诊断配置 / 跳转每日经营巡检
└── 每日巡检（作业三）
    ├── Skill 卡与订阅设置
    ├── 今日报告（总览）
    │   ├── 四维指标：流量 / 用户 / 交易 / 排名
    │   ├── 异常优先级和判断依据
    │   ├── 证据明细 / 比较基线 / 时间范围
    │   └── 建议操作 / 今日待办 / 继续分析
    ├── 历史巡检与跟进
    └── 执行记录与治理（演示 / 高级设置）
```

### 主路径

`进入每日巡检 → 查看或配置 Skill → 点击「模拟执行今日巡检」 → 生成本地执行记录 → 查看可交互报告 → 下钻异常/证据 → 标记行动 → 切换次日模拟数据 → 查看异常趋势与行动复盘`。

**关键衔接**：点击报告的「继续分析流量异常」应将店铺、指标、日期、异常和证据带入作业二已有诊断 S2，而非打开一个毫不相关的聊天页面。对于作业二只支持 `2026-11-14` 的受限数据范围，若选了其他日期，需提示范围限制或扩展真实 Mock fixture 后才能进入；绝不能展示旧数据伪装为当前日期结果。

## 3. Skill 卡：商家视图与机器视图

### 3.1 面向商家的可编辑配置

| 字段 | MVP 默认值 | 交互及校验 |
|---|---|---|
| Skill 名称 | 每日经营巡检 | 最多 36 字，可编辑 |
| 适用店铺 | 动燃健身旗舰店（虚构） | 单店固定，禁止越权店铺输入 |
| 监控范围 | 流量、用户、交易、搜索排名 | 多选，至少 1 项 |
| 时间与时区 | 每天 09:00，`Asia/Shanghai` | 可从允许的固定选项选择；展示数据完整性判断 |
| 对比基线 | 昨日 vs 昨日前、相似活动预期、连续排名快照 | 各指标分别标明适用基线，不混合口径 |
| 异常等级 | 严重 / 注意 / 信息 | 系统给出默认规则，MVP 不让普通商家随意改所有阈值 |
| 通知策略 | 仅重要异常提醒，其他日报归档 | 可改为每次巡检都提示（均为演示） |
| 执行权限 | 只读分析，不允许自动写操作 | 不可绕开 |
| 数据缺失处理 | 生成部分报告 + 明确缺口 + 待复核 | 不能自动补猜缺失指标 |
| Skill 版本 | `daily-business-pulse@1.0.0` | 可查看、不可直接手改内部版本号 |
| 订阅状态 | 未启用 | 保存后才允许开启；改配置后须重新保存/确认 |

**状态**：`draft → saved_disabled → enabled → paused`；可恢复。若编辑了监控指标/调度规则，原启用配置必须标记为待重新确认，避免「界面显示已订阅但执行的是旧配置」。

## 4. Mock 数据体系与业务事件脚本

### 4.1 复用作业二已实现的可信基线

当前仓库 `src/data.mjs` 已包含：

- 店铺 UV 口径 `SHOP_UV_001@v1.0`：北京时间自然日，四个互斥主来源渠道可求和至店铺 UV；
- 2026-11-11 峰值 UV = 10,000；11-14 实际 UV = 6,000；参考预期 UV = 7,000；
- 11-14 四渠道实际：付费 800、活动 2,050、自然 2,050、老客来源 1,100；参考预期：1,300、2,100、2,300、1,300；
- 相对峰值下降 4,000，参考正常回落 3,000，额外缺口 1,000；四渠道缺口 500 / 50 / 250 / 200；
- `missing-data` / `metric-conflict` / `timeout` 失败情景；
- 商品详情页 UV 只有口径没有完整日期值，不能直接取用店铺 UV 冒充。

**不得更改或破坏这组作业二锚点数据。** 本作业的时序 fixture 只是在此基础上扩展可用于日报、趋势、处理复盘的数据。

### 4.2 延展的课程模拟时序数据（建议固定值）

| 日期（北京时间） | UV 实际 | 相似活动/经营参考预期 | 业务脚本说明 |
|---|---:|---:|---|
| 11-11 | 10,000 | — | 11.11 大促峰值，不当作平日基线 |
| 11-12 | 7,600 | 7,800 | 活动结束后流量回落 |
| 11-13 | 6,800 | 7,200 | 广告计划可能异常，标记为「待排查线索」 |
| 11-14 | **6,000** | **7,000** | 锁定作业二锚点；额外缺口 1,000 |
| 11-15 | 6,500 | 6,900 | 商家已执行检查后的次日观察，不声明因果 |
| 11-16 | 6,800 | 6,900 | 与参考预期的差距进一步缩小 |
| 11-17 | 7,000 | 6,900 | 可作为基本恢复的展示示例 |

11-15 四渠道示例：付费 1,100 + 活动 2,050 + 自然 2,200 + 老客来源 1,150 = 6,500；参考预期 1,250 + 2,100 + 2,300 + 1,250 = 6,900，确保合计一致。11-12/13/16/17 也应有一致的渠道明细，或者只显示有数据支持的汇总，不能伪造分渠道图表。

### 4.3 四维数据口径（同日示例：2026-11-14）

| 维度 | 模拟指标 | 具体定义 / 守恒关系 |
|---|---|---|
| 流量 | 店铺 UV = 6,000；渠道 UV | 主来源互斥，每日四渠道之和等于店铺 UV；与作业二相同 |
| 用户 | 新访客 4,200；回访访客 1,800 | 当日二者互斥、相加为 6,000；**与「老客回访来源渠道 1,100」并非同一维度** |
| 交易 | 支付买家 180；支付订单 180；GMV ¥33,300；客单价 ¥185 | 示例人为设置每买家一单；支付买家转化率 = 180 / 6,000 = 3.0%，GMV = 支付订单 × 客单价 |
| 排名 | 固定关键字「普拉提弹力带」，前一可比快照第 6 位，当前第 12 位 | 采集条件固定（设备、地域、时间/搜索词），下降 6 位仅为告警线索，不能宣称导致流量减少 |

**退款率/广告 ROI 若无明确分子分母、归因窗口与真实可比数据，不作为首版硬性指标。** 如需展示，先补齐同口径 fixture 和测试。

### 4.4 业务事件与关联风险

- 11-11：活动峰值；11-12：正常回落；11-13：在事件日志中模拟「广告计划可能预算受限」，它是**待验证因素**，不是模型已证实的原因。
- 11-14：付费广告流量低于参考预期 500，优先排查；总 UV 比预期低 1,000。
- 11-15：模拟用户在待办中记录「已检查并恢复广告计划状态」；后续 UV 有改善，但报表只能写「观察到改善」，不能写「证明恢复操作带来 500 UV 增量」。
- 排名快照下降属于第二项观察线索；应要求继续核验曝光、点击和可售状态。

## 5. 异常检测、排序和防重复提醒

### 5.1 最小确定性规则

所有规则都应是可配置、可测试的纯函数，而不是让 LLM 即兴猜测阈值。

- **店铺 UV 预期缺口**：`(actual - expected) / expected ≤ -10%` 且 `expected - actual ≥ 200`，触发「需关注」。11-14：`-14.29%`、缺口 1,000，命中。
- **付费渠道**：与相似活动参考预期相比下降 `≥15%` 且绝对缺口 `≥200`，触发高优先级渠道排查。11-14：`500/1300 = 38.46%`，命中。
- **排名**：在可比采样条件下下降 `≥5` 名，标记待核验。第 6 → 第 12 位，命中；条件不一致则显示「不可比」，不触发确定性异常。
- **交易**：支付买家转化率/GMV 的同口径对比与异常判定，必须有可比基线；若无，则展示「数据观察」而不是硬判为异常。
- **用户**：新老访客构成变化只有在样本与可比基线完整时才报警；否则仅显示构成，不强行建议投放。

### 5.2 去重与优先级

- 每条告警 `alert_key = shop_id + metric_id + dimension + condition_id`，按日产生实例，并保留跨日持续问题的 `incident_id`。
- 同一个主问题可以有关联指标，但不能把店铺 UV 缺口与付费渠道缺口当作两笔互不相关的损失相加。
- 优先级优先考虑：影响幅度、是否连续、可执行性、证据完整度；不要用未经训练的「AI 置信度 xx%」。
- 每个告警附：阈值、实际值、比较基线、证据编号、排除事项、建议的下一步。

### 5.3 失败与降级

| 失败 | 行为 | 禁止行为 |
|---|---|---|
| 某维度缺数 | 输出部分报告，标注未覆盖项与原因 | 用其他渠道数据倒推缺失的用户详情 |
| 口径冲突 | 暂停受影响结论，显示差异与口径版本 | 静默选一个值冒充权威口径 |
| 排名快照不可比 | 仅显示当前采样值，取消趋势警告 | 用不同设备地域排名做连续比较 |
| 模拟超时 | 保留已完成指标与执行日志，允许重新运行 | 伪装完整任务成功 |
| 权限不符 | 拒绝并记录模拟审计 | 从本地配置修改权限跳过拦截 |
| 重复运行 | 相同店铺/日期/Skill 版本去重或显式标为重跑 | 默默产生多个相同通知 |

## 6. 可交互 HTML 报告规范

报告标题：「动燃健身旗舰店 · 2026-11-14 经营巡检日报」，模拟执行时间：`2026-11-15 09:00 Asia/Shanghai`。

### 6.1 信息层级（手机优先）

1. **顶部摘要**：数据日期、覆盖维度、是否完整、Mock 标志、执行时间。
2. **一句话决策摘要**：优先关注什么，哪些是正常变化，哪些仍不确定。
3. **四维 KPI 卡**：流量 / 用户 / 交易 / 排名；点击查看定义、基线、时间窗。
4. **异常列表**：按优先级排队，显示当前值、参考值、变化、证据完整度、状态。
5. **异常详情**：趋势或渠道拆解、证据元信息、口径解释、替代假设、推荐行动。
6. **今日待办**：`待处理 / 已处理 / 暂缓 / 不适用`，可写备注、记录操作时间。
7. **历史趋势与复盘**：切换日期、查看同一 incident 的状态变化，明确「相关性不等于因果性」。
8. **执行日志与技能版本**：主要给评审或高级使用者查看，默认折叠。

### 6.2 必须能操作的交互

- 点击四维指标切换详情；点击告警展开证据与建议。
- 报告日期切换至少覆盖 11-14/11-15/11-16，数值随日期真正变化。
- 告警可标记状态并持久化到浏览器本地；刷新后不丢失。
- 「继续分析该异常」可回到作业二对应的诊断流程（仅当该日期/指标有数据支持）。
- 技能配置可保存、暂停、恢复；模拟执行可生成可访问的历史报告和日志。
- 可在演示模式触发完整、缺数、口径冲突、重复巡检等情况，且与报告状态一致。
- 一键查看数据口径、版本和取数时间；无法取得的字段须显示「暂无数据」。

**交互式 ≠ 所有东西都要能编辑**：普通店长不能在报告页直接改指标原始值或改动受控规则。

| **调度网关** | 订阅频率、时区、数据就绪、去重/重跑、失败重试、Mock 通知 | 模拟「到点执行」入口、run log、通知策略 |
| **记忆层** | 保存关注指标、已处理告警、被否决建议、上次运行时间；按店铺隔离、时间戳和 TTL | 历史报告、待办状态、重复提醒抑制示例 |
| **自进化治理** | 从反馈生成「待审改进提案」，影子回放、对比评测、人工批准后发布、回滚 | 治理页/治理说明与版本记录；不得无审核自动改规则 |

### 7.1 记忆边界

- MVP 浏览器 `localStorage` 仅保存模拟技能配置、处理反馈、执行日志、报告快照；不可用于真实敏感商家资料。
- 每条记忆记录 `shopId, key, value, source, createdAt, expiresAt, version`；可删除和查看。
- 被「不适用」拒绝的建议可在固定短时窗口内去重（建议初始 TTL 7 日），但是发生新的重大异常仍应提醒。
- 历史建议不可无条件作为现在的事实，必须确认日期和数据版本。

### 7.2 自进化允许与禁止

**允许作为待审提案**：报告文案优化、异常卡排序方式、FAQ/解释模版；仅在 shadow run 与人工审核后生效。  
**禁止自动修改**：指标定义、数据权限、经营金额、广告预算、检测规则/阈值、金标答案、模型归因权重。  
**演示要求**：至少展示一次模拟「重复提醒被反馈 → 生成改进提案 → 待审核 → 模拟影子对比 → 批准/拒绝 → 版本记录」，不能直接宣称系统已经自我进化。

## 8. MVP、验收 KPI 与产品风险

### 8.1 MVP 必须完成

- 单店、只读、四维巡检；默认 09:00 模拟执行；三日及以上历史报告；重要异常优先级；证据卡；行动反馈；Skill 保存与订阅状态；模拟执行 Trace；缺数/冲突降级；一组治理示例。

### 8.2 明确不做

真实定时后台、推送服务、模型调用、营销计划自动执行、店铺跨租户授权、多 SKU 全量排名抓取、真实多店分析、自动调规则、真实经营 ROI 归因验证。

### 8.3 演示验收指标（不是实测商业 KPI）

| 指标 | 验收方法 | 目标 |
|---|---|---|
| 核心流程完整度 | 技能配置→模拟执行→日报→详情→反馈→历史 | 所有操作可点击闭环 |
| 数据一致性 | UV 汇总、渠道加总、GMV/转化计算、参考期 | 核心计算测试全部通过 |
| 告警可复核 | 每条告警可查看阈值、口径、日期、证据、来源 | 100% |
| Mock 失败保护 | 缺数、冲突、超时、无权限、重复运行用例 | 0 次伪装成功、0 次越权 |
| 反馈持久性 | 本地更新后刷新，历史状态仍在 | 必测通过 |
| 假订阅透明度 | 停止浏览器后不会继续执行，UI 明示模拟 | 100% 明示 |

真实商家采纳率、人工日报节省时间、异常准确率应留为未来调研/实测指标，不应把 Demo 的点击行为当成线上真实用户结果。

## 9. 开发与交付顺序

**P0 数据与核心闭环**：审查现有代码与测试，锁定作业二锚点；构建数据模型和纯函数异常规则；完成 Skill 卡、模拟执行、报告和证据下钻。  
**P1 持续服务**：日期切换、事件记忆、待办状态持久化、重复告警合并、模拟订阅/调度。  
**P2 治理演示**：可观测日志、版本/审批/影子验证示例、回滚、异常状态与移动端完善。  
**交付**：可访问 HTML 原型、技能卡交互、报告样例、多日演示脚本、README、若干截图、架构/设计说明和自动测试结果。

## 10. 工程约束与本地代码现状（2026-10-24 核对）

仓库不再是过去单一的 37KB `index.html`。目前公开主分支包含：

- `index.html`：入口，加载 `src/styles.css`、`src/app.mjs`；
- `src/app.mjs`：作业二 S1–S8、`initialSkill`、`merchant-diagnosis-skill-v1` 本地存储；
- `src/data.mjs`：前述诊断模拟数据和指标定义；
- `src/engine.mjs`：`DiagnosticTask` 状态机、`ApprovalFlow`、执行 Trace；
- `tests/data.test.mjs`、`tests/engine.test.mjs`：现有测试；
- `docs/走查记录.md`、`screenshots/`：作业二交付。

**实现原则**：保留现有作业二的 S1–S8 与测试。扩展 S8 为每日巡检入口时，旧本机配置通过清晰迁移逻辑转换为新的**默认未启用**配置，不可在扩展权限和范围后继承旧版自动启用状态。新增逻辑分模块（数据、规则、调度模拟、记忆、UI），但不必为作业强行引入 React、后端、数据库或外部 Agent 框架。
